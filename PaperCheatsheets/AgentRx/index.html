问题与目标

  • 长程工具轨迹中，最终报错和真正使任务失败的步骤可能不同。AgentRx 目标是定位第一个不可恢复的关键失败，并给出根因类别。

p.1 · 摘要 / §1

输入 → 中间产物 → 输出

  • 输入：任务指令、失败轨迹、工具 schema，以及可用时的领域策略。
  • 中间产物：统一轨迹表示 IR、全局与逐步动态约束、按步骤索引的违规日志 V。
  • 输出：关键步骤 ŝ、根因类别 ŷ、引用具体违规证据的简短解释。

p.5 · §3.1–3.4

原图标签对照

  • Task Context：任务上下文；Constraint Generator：约束生成器；Constraint Checker：约束检查器；Validation log：验证日志。
  • 阅读顺序：左上输入 → 中部生成断言 → 左下逐步检查 → 右侧违规日志 → 支撑失败归因。

p.1 · Fig.1

全局约束 Cᴳ

  • 从工具 schema 与领域策略生成一次，放入全局存储。它描述跨轨迹步骤适用的接口要求和业务规则。

p.5 · §3.1–3.4

动态约束 Cᴰₖ

  • 结合任务与截至第 k 步的轨迹前缀生成，利用已有工具返回等局部事实；每一步可用约束 Cₖ = Cᴳ ∪ Cᴰₖ。

p.5 · §3.1–3.4

检测与最终判断分离

  • 违规是诊断证据，不是不可推翻的硬结论。judge 可以依据完整轨迹上下文覆盖噪声约束，并区分可恢复错误与关键失败。

02 / 可执行检查怎样帮助定位

AgentRx 是诊断框架：论文的主要评估关注步骤定位与根因分类，没有报告自动修复后的任务恢复率。p.6 · §4.1–4.2

处理流水线｜5 步

  1. 规范化：把不同系统日志映射成统一 IR，保留步骤、agent、工具、输出与对话等字段。
  2. 合成约束：生成全局规则，并随轨迹前缀生成动态规则；每条规则都有触发 guard 与待验证断言。
  3. 逐步检查：guard 不满足就跳过；满足时，用代码检查结构化字段，或用 LLM 检查语义谓词。
  4. 记录证据：只把违反的约束连同步骤 k 和证据 e 写入 V，得到可审计的违规序列。
  5. 根因裁决：judge 读取任务、轨迹、分类 checklist、V，挑出足以解释任务失败的最早关键步骤，并给出类别与理由。

p.5 · §3.1–3.4

guard 与 assertion 的分工

  • guard：这条约束在当前步骤是否适用？例如当前是否调用了指定工具或由指定 agent 发言。
  • assertion：在适用时是否满足要求？返回 SAT 或 VIOL，并附支持证据；guard=false 则返回 SKIP。

p.5 · §3.1–3.4

原文例子｜商品数量

  • 工具返回商品信息后，assistant 宣称有 11 个 T-shirt 选项。AgentRx 生成 tshirt_count_matches 关系约束，检查数量是否来自正确返回字段。
  • 违规日志把“数量说错了”变成“第 7 步输出与第 6 步工具返回不一致”的可追溯证据，支持归类为误读工具输出。

核心思路

先把任务要求和工具语义变成可检查约束，留下具体违规证据，再让 judge 定位第一处不可恢复的失败。

已有做法与具体不足本文的对应设计
只让 LLM 通读失败日志，定位理由可能缺少可核查依据先生成并执行约束，提供逐步违规证据。
MAST 的广义分类和 Who&When 的责任位置不足以直接解释不可恢复点在当前定义下联合判断关键步骤与根因类别。

依据本文引言、相关工作及方法压缩整理；对照仅针对列出的做法。

创新点｜具体改了什么

  • 全局规则与按前缀变化的局部规则组合。
  • 把约束验证与最终归因分开，避免把任一违规直接当根因。
