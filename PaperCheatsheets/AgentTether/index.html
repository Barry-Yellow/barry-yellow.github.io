02 / 从依赖图到受控干预

系统先观察初次运行；初次失败后才启动修复循环。实验最多允许三次修复迭代。p.7 · §III.D / IV.A

诊断路径｜4 步

  1. 定义 TU：每个单元含观察 o、信念 b、动作 a、反馈 f，代表一个决策—执行—反馈周期。p.4 · §III.A–B
  2. 构造 CTG：时间边连接相邻 TU；依赖边连接共享状态、产物或错误签名的 TU，支持跨时间步回溯。p.5 · §III.C
  3. 圈出异常：离线 HGT 学习成功遥测的结构与属性，给出异常分；运行内 Isolation Forest 使用 25 维局部特征；两类异常区域取并集。p.5 · §III.C
  4. 生成指导：保留高分转折候选、检测证据及最小依赖邻域；LLM 返回根因、确认转折点、恢复建议，再转成短指令与注入计划。p.6 · §III.C.3 / III.D

干预路径｜3 个判断

  1. Check：检测重复工具调用、意图漂移、预期修正未实现、指导被延迟或遗忘。p.6 · §III.C.3 / III.D
  2. Decide：要求证据支持；通过冷却、次数限制和去重防止过度干预；选择扰动最小的响应。p.6 · §III.C.3 / III.D
  3. Inject：工具返回时把纠正附加到工具结果；文本响应时可插入合成 user 消息并让 agent 继续。预期修正完成后停止干预。p.7 · §III.D / IV.A

原文例子与设计意义

  • 银行任务中，存支票调用遗漏 check_amount，使存款失败；随后转账因余额不足失败。只看末尾报错会忽略上游遗漏。p.2 · Fig.1
  • 图上的依赖回溯帮助找到先前动作；指导针对错误动作族与约束类别，避免直接硬编码实例答案。p.6 · §III.C.3 / III.D

结果与适用边界

  • 261 个 τ-bench 任务中，初次失败的 123 个 Qwen3.7-max 任务为修复对象，修复 85 个（69.11%）；此分母不是全部 261 个任务。p.7 · §IV.B
  • Banking：Qwen3.7-max 恢复 49/83（59.04%）；GPT-5.4 恢复 56/86（65.12%）。p.1 · 摘要
  • 它依赖完整运行日志、检测器与辅助模型；主要证据来自三个有状态工具任务域。p.7 · §III.D / IV.A

核心思路

把失败后的依赖图诊断和下一轮运行中的受控干预连接起来，让正确的修复建议在长任务中持续生效。

以前文章的问题 → 本文如何解决

已有做法与具体不足本文的对应设计
只看相邻步骤容易把末端报错当源头沿 CTG 的非局部依赖回溯早期转折。
Reflexion/Self-Refine 式一次性反馈在长执行中可能被遗忘在线检测偏离并按需纠正。
过于频繁干预可能打断正确行为设置证据门槛、次数限制、冷却及停止条件。

依据本文引言、相关工作及方法压缩整理；对照仅针对列出的做法。

创新点｜具体改了什么

  • 诊断路径与运行时控制路径协同，既找问题又监测修正是否落实。
  • Repair Memory 区分已修复与未解决事项，避免反复推翻已有修正。
最吸引人的点 （整理者判断）

它关注的不只是“给一条好建议”，而是“执行到一半时，这条建议还在起作用吗？”

创新点为贡献归纳，不作未经全面核验的首次声明；亮点为整理者判断。
