一句话读懂

输入漏洞描述与 sanitizer 报告，先并行取结构、运行、历史证据，再把统一上下文放入持久记忆，使修复 Agent 多轮生成与验证补丁。

p.5 · Fig.3 · §III-C

原架构图｜证据形成 C，再经 M 支撑修复

原图：三个分析子 Agent 操作同一沙箱环境，产出 Cstruct / Cexec / Chist；Arepair 在持久情景记忆 M 中使用这些证据，输出补丁 P。p.5 · Fig.3 · §III-C

问题｜普通代码导航缺少安全相关证据

  • 结构：跨文件数据流、控制条件、内存分配与所有权关系。
  • 运行：崩溃位置、内存来源、栈帧与错误类型。
  • 历史：导致脆弱模式的提交及其设计意图。
  • 任务入口：已有漏洞描述和 AddressSanitizer 报告；本文评估不是从零发现漏洞。

p.4 · §III-A/B

方案｜两阶段，不是四个 Agent 混聊

  • 取证阶段：Astruct、Aexec、Ahist 并行，以 ReAct 调用各自工具并压缩结果。
  • 修复阶段：Arepair 持续使用统一上下文，生成最小候选改动。
  • 验证循环：应用补丁 → rebuild → 执行 PoC 与 sanitizer → 不通过就继续修复。

p.5 · Fig.3 · §III-C

这里的 memory 是什么

  • 框架：〈V,E,A,C,P〉；漏洞输入、沙箱、四角色、三类证据、候选补丁。p.4 · §III · formalization
  • 保存：压缩的三类分析证据，不逐字存整个仓库。p.4 · §III-A/B
  • 作用：让 Arepair 多轮修复持续看到同一组上下文。p.4 · §III-A/B

模型与步数｜本论文的配置

  • 模型：GPT-5.2（medium reasoning，T=1.0）。
  • 预算：分析者各 20 步，修复者最多 75 步。
  • 工具：ToolCallingAgent JSON 调用；Docker 隔离。

p.6 · §IV-D

  • Program Context / Episodic Memory / Repair Patch：程序上下文 / 情景记忆 / 修复补丁。

原运行证据 Fig.5｜崩溃从哪里发生

案例阅读顺序｜症状、原因、修改、再验证

  • 症状：闭包销毁时访问已失效的 function_name。
  • 结构证据：创建时借用指针，销毁却按自有引用释放，生命周期假设不一致。
  • 历史证据：此前对 call-magic 名称稳定性的特殊处理，在 trampoline 分支留下不一致。
  • 修复方向：在两个构建位置复制引用，而不是把崩溃路径直接跳过。

p.7 · Fig.4 · PHP 案例

Cstruct｜代码结构上下文

  • 先定位：按漏洞描述与 sanitizer trace 确定受影响的文件、函数和漏洞类型。
  • 取证：跨文件数据流、taint 路径、控制流与内存操作关系。
  • 交付：位置、数据流摘要、结构性风险及高层修复方向。

p.4 · §III-A/B

工具专长｜早期分工

  • 结构分析者早期主要使用 CodeQL；后续更多转向命令行仓库检查。

p.10 · Fig.7 · §VI-C

Cexec｜运行执行上下文

  • 复现：在动态 instrumentation 下触发 harness。
  • 观测：崩溃地址/类型、完整 backtrace、内存访问和异常状态。
  • 交付：关键栈帧、内存状态、运行根因与修复建议。

p.4 · §III-A/B

工具专长｜运行取证

  • 运行者早期使用 GDB、Valgrind 等；最终补丁还要回到执行反馈。

p.10 · Fig.7 · §VI-C

Chist｜提交历史上下文

  • 范围：从受影响文件/函数出发，检查漏洞 base commit 之前的历史。
  • 取证：提交元数据、变更摘要和历史修改上下文。
  • 交付：相关提交、改动关联性、漏洞来源与修复方向。

p.4 · §III-A/B

工具专长｜历史取证

  • 历史分析者早期使用 PyDriller；所有上下文最终由 Arepair 整合。

修复仍是主要工作｜作者的轨迹统计

核心思路

先由专门 agent 建立代码结构、运行执行、提交历史三类证据，再让修复 agent 带着这些证据迭代生成补丁。

以前文章的问题 → 本文如何解决

已有做法与具体不足本文的对应设计
函数级漏洞修复难以覆盖跨文件关联使用可访问整个仓库的 agent 与结构分析。
普通仓库修复框架有工具，却未必组织出安全相关证据把静态结构、运行语义和提交历史显式分工并汇合。

依据本文引言、相关工作及方法压缩整理；对照仅针对列出的做法。

创新点｜具体改了什么

  • 核心变化是多面程序上下文工程，而非简单增加聊天角色。
  • 分析与补丁生成分阶段，证据通过记忆持续提供给修复者。
最吸引人的点 （整理者判断）

同一个崩溃从“代码怎样关联、执行时发生什么、历史上为何变成这样”三个角度交叉解释。

创新点为贡献归纳，不作未经全面核验的首次声明；亮点为整理者判断。
