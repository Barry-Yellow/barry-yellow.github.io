多智能体 LLM 系统为什么会失败？

Why Do Multi-Agent LLM Systems Fail?

Mert Cemri、Melissa Z. Pan、Shuyi Yang 等 · UC Berkeley / Intesa Sanpaolo
首发 2025-03-17；本表使用 arXiv v3 · 2025-10-26（版本日期不等于首发日期）
本地论文首页标注 NeurIPS 2025 · Datasets and Benchmarks Track。 官方版本 · 本地 PDF · 代码与标注工具 · MAST-Data
核心思路

“任务失败”这个总分看不出系统坏在哪里。作者先逐条研究真实协作日志，把反复出现的问题整理为 14 种失败模式、3 大类，校准人类与 LLM 的标注，再用统一标签分析不同系统，并据此尝试改角色、终止权限和验证流程。

研究对象与输出：先分清本文做什么

输入：多 agent 的任务、角色/流程与完整交互日志，以及任务是否达标的反馈。

输出：可复用分类体系 MAST、带模式与理由标注的 MAST-Data、可扩展标注器，以及失败分布和设计改进案例。

它提供的是“失败模式语言与证据资源”，不是给每次失败自动确定唯一根因、回滚或搜索补丁的通用修复算法。

① 从日志中发现模式

先取 5 个框架的 150 条轨迹，6 位专家用 Grounded Theory（扎根理论）开放编码、反复对比和记录解释；先观察数据，再归纳概念，不先预设固定错误清单。

② 迭代定义，减少歧义

3 位标注者独立标注、讨论分歧、修改定义；3 轮、每轮 5 条的研究达到平均 κ=0.88。另发布的 MAST-Data-human 有 21 条多专家标注轨迹，不能混作 1642 条全部人工核验。

③ 用校准后的 LLM 扩大标注

o1 读取轨迹、分类定义和 few-shot 人工案例，输出模式与理由；以人工标签校准，再用于 7 个框架的 1642 条日志。LLM 负责扩展规模，人类一致性不等于因果真值。

来源：§3.1–3.2；标注器/数据规模见 p.6 · PDF p.5

原文案例 Fig.3｜不是“密码错了”这么简单

沿一个输入走通 MAST 的分析

  1. Supervisor 给 Phone Agent 邮箱式 username 和密码，要求登录。
  2. Phone Agent 读到 API 文档：username 实际应为手机号，却照原参数调用，收到 Invalid credentials。
  3. 它只回报“凭据不正确，请提供正确帐号密码”，没传达已观察到的格式要求，因此标为 2.4 信息隐瞒/未共享。
  4. 上游也没追问缺什么条件，可能另出现 2.2 未澄清。分类帮助确定应检查的信息流；要声称某改动能救任务，还要另做干预验证。

FC1｜系统设计问题

角色、任务、上下文与结束规则的设计/遵循。

模式中文判断线索
1.1 任务规格没遵守任务约束/需求。例：要求动态选词，却写死词库。
1.2 角色规格越过职责或权限。例：不该终止讨论的角色作了终止决定。
1.3 步骤重复反复做已完成的步骤，不产生必要新进展。
1.4 历史丢失近期上下文被截断/忽略，退回较早状态。
1.5 不懂终止条件不识别何时已达完成条件，可能无谓继续。

FC2｜agent 间不对齐

信息如何被传递、理解和转成行动。

模式中文判断线索
2.1 对话重置无根据地重启对话，丢掉已取得的进展。
2.2 未请求澄清信息模糊或不全时仍依假设继续。
2.3 任务偏航逐渐偏离原目标，转向不相关工作。
2.4 信息未共享持有别人决策所需的信息，却没有传达。
2.5 忽略同伴输入信息已经传来，但没有充分考虑/使用。
2.6 推理—行动不符说应采取 A，实际却执行不相符的 B。

FC3｜任务验证

什么时候结束，以及检查是否足够/正确。

模式中文判断线索
3.1 过早终止目标或信息交换未完成，就结束任务/对话。
3.2 未验证/验证不全缺少必要检查；只编译代码却不测任务规则。
3.3 验证错误进行过验证，但检查或结论本身不正确。
最值得记住的点（整理者判断）

“加一个 verifier”不是答案。它究竟检查了什么、是否覆盖高层任务目标、谁有终止权，比模块名字更关键。

相似症状，先问信息在哪一环断了

  • 信息未共享 2.4：日志支持某 agent 已掌握关键信息，但没有转交。
  • 忽略输入 2.5：别人已经说了，却没有被接纳或使用。
  • 历史丢失 1.4：对所需上下文的保留/访问出问题。
  • 未澄清 2.2：不确定时本应问，实际继续假设。仅凭最终答案错误，不能断言是哪一种。

来源：§4 FC2；定义 Appendix A · PDF p.7

从标签到改进：不要跳过中间证据

建议的阅读/使用顺序是：任务要求 → 具体消息/动作证据 → 对照模式定义 → 标注理由 → 汇总分布 → 设计改动 → 再观察任务与模式变化。这是基于论文实践的使用归纳，不是一个新算法。

一个失败运行可暴露多个模式；模式常共现，不应强制只选一个。比如错角色先终止，与验证没覆盖目标可以共同出现。

MAST 主要标注行为/设计层面的失败模式。它不能仅凭标签给出“纠正这一步一定阻止失败”的反事实保证。

来源：§5.2–5.3；因果保证边界为整理者根据任务范围归纳 · PDF p.9

具体贡献：把“为什么失败”变成可比较对象

  1. 跨系统经验词表：用真实日志底向上形成 14 模式与定义，并以人类分歧反复修订；“第一套”是作者贡献声明，本表不据此独立证明新颖性。
  2. 数据与标注工具：将分类、理由和任务日志一起发布，支持研究不同系统、模型和任务的失败画像。
  3. 面向设计的反馈：不只问成功率升了多少，也看角色/拓扑改变减少了什么模式、还剩什么模式。

真正改了什么？两组案例

AG2 / MathChat：基线 Student + 可执行 Python 的 Assistant。提示改进加入结构与验证；拓扑改进分成 Solver、Coder、Verifier，且仅 Verifier 能结束讨论。用 GSM-Plus 随机 200 题、两种模型、6 次重复评价。

ChatDev：提示改进约束角色权限并强调任务边界；新拓扑从单向 DAG 改成循环反馈，由 CTO 确认评审满足后才结束，并设迭代上限。ProgramDev-v0 是 32 个自建程序任务，另测 HumanEval。

论文支持什么，不支持什么？支持“在这些任务与配置中，角色、验证和交互结构值得系统地调整”；不支持“某标签自动对应一个必胜补丁”。组合干预不能把全部增益归给单一机制。开发分类的初始样本、完整数据与各比较子集也不是同一分母。

使用边界与易误读点

  • 作者明确不声称 14 模式覆盖所有失败；新领域或新 agent 形态仍可能需要新定义。
  • 框架间任务/模型配置不同。Fig.4 是系统特征画像，不能用柱高直接做公平排行榜。
  • 大规模标注使用 LLM，可能有漏标/误标；高一致性不排除共同误判，也不证明机制因果关系。
  • 论文主要产出数据、分类和标注流程。它没有把 checkpoint、干预选择和恢复执行做成通用自动修复器。
  • Table 1 列的是 7 个框架；§3.4 的名单表述又提到 Manus，不能擅自把它再算成已统一确认的第 8 个框架。

重要参考文献：理解这篇需要的近邻

  1. Which Agent Causes Task Failures and When? On Automated Failure Attribution of LLM Multi-Agent Systems

    Who&When 定义“责任 agent＋决定性步骤”归因任务。与 MAST 的“失败属于什么模式”互补，不能把模式分类准确率和步骤定位准确率混为同一指标。

  2. AutoGen: Enabling Next-Gen LLM Applications via Multi-Agent Conversation

    可定制的 agent、工具和对话编排框架。是理解 AG2/MathChat 宿主与角色协作的基础背景。

  3. ChatDev: Communicative Agents for Software Development

    以角色化 agent 对话连接设计、编码和测试。MAST 对它做了角色权限与循环评审的干预案例。

读完应能这样复述

MAST 先从真实失败日志归纳模式，再用一致性研究把定义写清，借 LLM 标注器扩大到 1642 条轨迹。它让开发者看到问题属于角色/状态设计、agent 信息协作还是验证，并用案例说明调整系统可能有帮助。它的主张是系统设计也会制造失败，不是把所有失败都归结为模型弱，也不是已经实现自动根因证明与通用修复。
