日志分层图 → 子任务 oracle → 回溯/控制与数据筛查 → 排除自纠正

拿一个输入走通方法

检索子任务应产出符合日期的证据，计算子任务应基于它求数值，汇总者给最终答案。

  1. 为子任务写虚拟 oracle：目标、前提、关键证据和验收标准；再把实际步骤对齐到子任务/agent/OTAR。
  2. 若计算结果不满足 oracle，先查其输入：输入本已错就沿数据边追检索源；输入正确而计算变错才留在当前步。
  3. 若根源是反复下达不合理方案，检查规划控制；若方案已改而执行继续出错，则另看执行责任。
  4. 再回看后续是否已修正该偏差；已被修复的暂时错误不作为最终失败的决定性来源。

关键设计为什么需要

oracle 给中间行为一个明确检查目标，而不是只看最终答案。它由模型生成并作语义判断，并非可靠的外部真值，也没有真实反事实续跑。

术语就地解释

OTAR：观察、思考、行动、结果；虚拟 oracle：模型生成的中间验收条件，不是天然正确的裁判。

方法：按执行顺序读

  1. 分解并对齐：检索类似任务的分解示例生成子任务，随后对照实际日志反思修正，避免计划与执行不符。
  2. 解析并连边：agent 用 OTAR（观察／思考／行动／结果）表示；连子任务逻辑边、协作边与带输入输出快照的数据依赖边。
  3. 合成 oracle：为子任务生成目标 G、前置条件 P、关键证据 E、验收准则 C，作为中间检查依据。
  4. 逐层回溯：按子任务逆拓扑检查输出，再下钻 OTAR 异常的 agent，最后检查与 oracle 不符的原步骤。
  5. 筛除传播症状：先查局部输入是否有效；非局部错误分别检查规划控制和数据流，追到最初把有效数据变坏的地方。
  6. 排除可逆偏差：查看后续轨迹是否重新满足 oracle；已自纠正者不承担最终根因责任，再确定决定性 agent／步骤。

前作不足 → 本文设计

相关做法的不足本文如何处理
平坦轨迹难看清规划、工具与协作依赖HCG 加上 OTAR 和显式步骤数据流。
只有最终成败、缺少子任务监督合成“目标／前提／证据／验收”虚拟 oracle 后分层剪枝。
ECHO 式层级上下文或直接判断易混淆源头与症状沿控制与数据依赖筛查，并排除后续已经修复的偏差。

判断依据、差异与阅读边界

沿原文核对中间产物和接受条件；原图可点击放大。p.4 · §4.1–4.2 · Fig.2

判断依据与关键细节

  • 虚拟 oracle Oₖ=〈目标、前置条件、关键证据、验收准则〉：生成后仍由 LLM 作语义比较。
  • 局部归因：没有上游触发因素，且有效输入在当前步骤变成错误输出，才把责任留在当前步骤。
  • 规划控制：重复同样计划并忽略错误信号偏向规划责任；规划已合理改变而执行持续异常，偏向执行责任。
  • 数据流：核对边上的变量与输入输出，追踪错误数据首次产生处。
  • 证据边界：文中“反事实”主要是基于已有日志的语义筛查；框架强调无需重新执行环境。

实验能说明什么

  • 作者结果：DeepSeek-V3.2 在 Algorithm-Generated 上，有最终正确答案时步骤准确率 52.00%；无该答案时为 45.60%。
  • 边界：在 Who&When 单根因设定下评价；图边和虚拟 oracle 的错误会向下传播，未证明多根因或更广泛环境下可靠。

相对近邻的变化

  • 层级不仅是上下文压缩，还直接决定子任务→agent→步骤的诊断搜索顺序。
  • 虚拟 oracle 提供可阅读的中间检查目标，减轻只依靠最终正确答案的问题。
  • 以局部／非局部、控制／数据和偏差可逆性逐步区分责任。
