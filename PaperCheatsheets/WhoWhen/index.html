Who&When：哪个 agent，在什么时候，引入了决定性错误？

Which Agent Causes Task Failures and When? On Automated Failure Attribution of LLM Multi-Agent Systems

作者：Shaokun Zhang、Ming Yin、Jieyu Zhang、Jiale Liu 等 11 人。主要机构：Penn State、Duke、University of Washington、NTU、Meta、Google DeepMind、Oregon State、AG2AI。
版本：arXiv v3，2025-06-02；首发 2025-04-30。发表：ICML 2025 / PMLR 267。本表按所存 v3 的图表整理，版本日期不等于录用日期。

核心思路：最终答案错了，只能说明系统失败，不能告诉开发者该改哪个组件。本文把“读失败日志，预测责任 agent 与最早决定性步骤”定义成可评测任务，建立人工标注的 Who&When 数据集，再比较三种 LLM 裁判阅读日志的方式。它是归因任务与基准工作，不是自动修复/回滚算法。

输入、输出和“决定性”的含义

输入：问题 Q、失败日志 L；可提供系统角色/工具/提示信息。评测分“知道最终正确答案”与“不知道答案”两种设置。

核心预测：责任 agent î 与原日志步骤 t̂。人工标签另含自然语言理由；全文/逐步提示也要求解释，二分提示只做区间分类。普通局部错误、最终报错和决定性错误不必是同一位置。

Δᵢ,ₜ(τ)=1 ⇔ 原轨迹失败，
固定前缀、改正 (i,t) 并相应调整后续后成功。
(i*,t*) = 满足 Δ=1 的最早 agent–时间对。

i 是行动 agent，t 是离散轮次，τ 是执行轨迹；Δ 是概念上的反事实判据，随后取最早 t。原文 Z=1 表示失败，Z=0 表示成功。

§3.1 · PDF p.3 Hand-Crafted · PDF p.4

标签怎样来？

三位专家先独立分配标注，记录责任 agent、步骤、原因及不确定项；随后讨论不确定案例，追求共识；最后交叉检查、必要时重标。

专家必须查浏览历史与信息源。共识提高一致性，但不自动消除单根因选择的主观性。

§3.2–3.3 · PDF p.4

先记一条主线：阅读范围不同 → 决策时机不同 → 容易犯的错不同

① All-at-once：全文一次判断

拿到：Q ＋完整日志；有答案设置另给最终 gold answer。

处理：一次提示让裁判跨 agent 阅读完整过程，输出责任 agent、首次出错步骤与理由。

优势：能看见谁的错误影响了后来，利于比较不同 agent。

风险：整体判断对了，仍可能在长日志里指错精确位置。

② Step-by-step：读前缀、遇错停止

第 i 次拿到：Q ＋日志前缀 l₁…lᵢ。

处理：问“当前最新行动是否有会妨碍解题的错误？”判断 Yes 则立即返回该条的 agent 和 i；No 则继续。

优势：逐个行动检查，决策更贴近具体步骤。

风险：看到后续前已停止；可恢复小错可能被过早认作决定性错。

③ Binary search：判断半区、缩小范围

拿到：Q ＋当前候选日志区间。

处理：二分区间，让裁判判错误在哪半，保留那半再二分，直到定位一条；返回其 agent 与步骤。

优势：在全文和逐步之间折中调用次数与上下文。

风险：半区判断若错，真实步骤被丢掉；LLM 判据并不具备传统二分查找的可靠性保证。

把一个例子走一遍

帮助理解的示例：问题需要真实房屋成交价。①协调者分配查价；②检索者没找到数据；③分析者用模拟表填数；④协调者把它当真实价格作答。

  • 全文读：裁判同时看到失败答案与全部来源，可把原因追到③；但也可能只指出④的发言位置。
  • 逐步读：到②可能误把正常“暂未找到”当致命错并停止；如果继续，到③才可能识别以假数据代替证据。
  • 二分读：先判断①②还是③④，再细分；若缺少完整任务语境或一次分支选错，就可能错过③。

应学到：“它说了一句错话”还不够，要问其是否是最终失败的决定性来源、是否在后面修正。此示例只解释协议，不是论文实测预测结果。

为什么步骤编号很容易混？

一个 step 是日志中的一条行动/发言记录，不是“这个 agent 第几次说话”。Appendix G 示例用 0-based 编号：第三条发言对应 step 2。

Appendix A 的数学伪码写 l₁…lₙ；实际使用时应核对数据字段与实现的编号约定，不能仅凭文中 i 直接套索引。

二分表述边界：§4.1 与 G.2 写 upper/lower-half 选择；A.3 伪码写检测左半是否含错再收缩。这里按“二分式归因”讲共性；未运行代码，不声称这些描述逐行完全相同。

作者贡献的压缩归纳：研究问题形式化、Who&When 数据资源、归因协议的系统性比较。这里不宣称已独立证实“首次”，也不把三种协议当成保证正确的根因算法。

三种指标，不能混成一个“准确率”

  • Agent accuracy：î 是否等于标注责任 agent。
  • Step accuracy：t̂ 是否精确等于标注步骤。
  • Tolerance ±k：是否满足 |t̂−t*|≤k。放宽容忍范围不等于更精确定位。

论文把 agent / step 分别评估；没有把“找对 agent”当“步骤也找对”。判对位置也不代表修改后一定恢复。

什么没有被本文解决？

  • 标签不是实验式因果证明：专家讨论与复核依赖领域判断；一致不等于每条都经可控重放验证。
  • 单个最早标签有表达边界：多处错交互时，选一个 principal error 不能完整描述联合修复集合；这是对任务设定的整理者解读。
  • 数据范围有限：184 条、两个通用助理任务来源；手工日志可达 130 条，算法生成日志最多 10 条，长度差会影响比较。
  • 已失败后的离线诊断：没有证明在线预警或修复恢复率；没有新训练出来的专用归因模型。
  • LLM 判断机制本身会误判：更强推理模型也未在所测设置下稳定解决精确定位。

读完应能复述：它收集自然失败日志，请人标出 who 和 when，然后让 LLM 用不同阅读协议预测这些标签。难点不是发现最后一句错了，而是从跨 agent 的长过程里找出最早决定性来源。

重要参考文献｜为什么要看它们

  • Adaptive In-conversation Team Building for Language Model Agents：Captain Agent 动态组队、配置专业角色；是 Who&When 算法生成系统的来源。
  • Magentic-One: A Generalist Multi-Agent System for Solving Complex Tasks：由 Orchestrator 协调浏览、文件、代码等角色；是手工系统失败日志的来源。
  • GAIA: a benchmark for General AI Assistants：真实世界问题，涉及推理、浏览和工具；是本文 query 来源之一，原任务成功评价不等于归因标注。
  • AssistantBench: Can Web Agents Solve Realistic and Time-Consuming Tasks?：现实且耗时的网页任务，是另一任务来源；帮助理解为什么标注者需要查网页与浏览过程。
