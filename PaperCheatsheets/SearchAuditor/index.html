要解决什么

  • 长搜索轨迹中，错误常被后续流畅推理掩盖；直接通读容易抓住后期症状，漏掉早期关键决策。

p.5 · §4

输入 → 输出

  • 输入：问题 q、错误答案 â、完整失败轨迹 τ；审计器不拿标准答案。
  • 输出：关键步骤 k̂、六类根因之一 ĉ、过程级修复指令 r̂。

p.2 · §3

对象与范围

  • 审计对象是长程搜索 agent；多个审计角色使用同一底座的不同提示配置，不是分别训练的模型。

p.5 · §4

图中蓝色｜整体审计

  • Holistic Audit：直接分析完整轨迹，找出关键步骤、根因与理由，补充专门流程可能漏掉的错误。

p.5 · §4

图中绿色｜反向约束审计

  • Backward Constraint Audit：拆出问题约束，追溯缺乏证据支持的约束，找到最早未经验证就锁定方向或答案的决策。

p.5 · §4

图中橙色｜正向时间线审计

  • Forward Timeline Audit：先建立覆盖题目要求的最小计划，再顺序扫描决策，寻找最早使执行走向失败的步骤。

02 / 执行流程与结果口径

关键设计：把“提出诊断”与“裁决诊断”分开，裁决依据是原始消息证据。p.5 · §4

从轨迹到修复｜5 步

  1. 并行审计：三个分支各输出候选关键步骤、根因、理由；专门分支还输出审计笔记。p.5 · §4
  2. 整理证据：列出分歧，对相近候选步骤分组；抽取候选处与最终答案附近的原消息窗口，同时生成全局决策提纲。p.5 · §4
  3. 证据裁决：共同决定步骤与根因，引用支持消息；允许少数意见胜出，也允许从不同报告组合一致的步骤—根因。p.5 · §4
  4. 生成修复：固定诊断后，用问题、错误答案、诊断及关键位置窗口生成过程指令；指令说明如何重新搜索与验证。p.5 · §4
  5. 恢复执行：在恢复实验中保留至预测关键步骤的轨迹前缀，把修复作为 user 消息附加，然后按原执行框架继续。p.7 · §5.4 / Table 4

原文例子｜截止日期约束

  • 问题要求截至 2025-05-01 引用数超过 25 万的 AI 论文。agent 在第 29 步把 2026 年的引用数当成证据，错误接受 Vaswani。
  • 根因：忽略约束（Constraint Neglect）。修复：把日期设为硬约束；核对截止日引用数和作者顺序，而非直接塞入标准答案。

p.1 · Fig.1

裁决怎么选步骤

  • 若工具调用本身错误，定位发起该调用的决策；否则定位首次误用工具返回的决策。关键标签是 assistant 决策，不是工具返回消息。
  • 报告一致只是线索，不用简单多数投票代替证据。

p.5 · §4

审计基准上的表现

  • SearchAuditBench：1,243 条失败轨迹，平均 73.1 条消息、65.1K tokens。p.2 · §3
  • GPT-5.5 下 FPS = 32.26%，最强基线为 26.55%。FPS 要求步骤落在容忍区间、根因正确，且修复满足全部专家 rubric。p.6 · Table 2

真正续跑后的恢复

  • LiveBrowseComp：Kimi-K2.6 的 213 条可评分失败中恢复 17.37%；Quest-35B 的 300 条失败中恢复 10.33%。
  • 32.26% 是审计完整通过率，不能当作实际任务恢复率；后者来自独立的续跑实验。

核心思路

让整体、反向约束、正向时间线三个视角分别审计，再回到原消息证据裁决，生成从关键位置起可执行的搜索修复。

以前文章的问题 → 本文如何解决

已有做法与具体不足本文的对应设计
单次通读容易被流畅的后期推理误导用三个互补视角提高早期错误召回。
简单投票可能把共同误判放大用原始消息证据裁决，允许少数诊断胜出。
只有错误标签不能指导恢复另生成过程级搜索修复指令并独立测试续跑。

依据本文引言、相关工作及方法压缩整理；对照仅针对列出的做法。

创新点｜具体改了什么

  • 约束回溯与时间线扫描互补，再由证据而非票数定案。
  • 将关键步骤、根因及可执行修复纳入统一审计目标。
最吸引人的点 （整理者判断）

它不只问“答案为什么错”，还问“哪一条题目约束第一次被未经验证地当成满足了？”

创新点为贡献归纳，不作未经全面核验的首次声明；亮点为整理者判断。
