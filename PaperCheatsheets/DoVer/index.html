DoVer: Intervention-Driven Auto Debugging for LLM Multi-Agent Systems

Ming Ma, Jue Zhang, Fangkai Yang, Yu Kang, Qingwei Lin, Saravan Rajmohan, Dongmei Zhang

一句话读懂

DoVer 保留干预点前缀，只改变可疑指令或计划，再继续执行；用干预后的成功、进度与执行忠实度检验假设。

原架构图｜四阶段 Do–then–Verify

原图：按重新规划切成 trial，每段提出假设并独立干预；斜线块是重放产生的新规划/执行。p.5 · Fig.2 · §4

输入轨迹｜消息之外，还必须记录恢复状态

符号含义在调试中的作用
aₜ活跃 Agent定位消息作者
mₜ该步消息可被替换的协调指令或计划
σₜ历史上下文与必要状态恢复原执行位置，继续调用工具/模型

p.6 · §4.1

问题｜单步归因不一定有唯一答案

  • 多次尝试：一个会话包含多轮策略，每轮都可能有决定性错误。p.4 · Fig.1 · §3
  • 协调歧义：错误指令与错误执行会同时发生，责任不能总压到单个 Agent。p.4 · Fig.1 · §3
  • 标签不确定：作者复核 29 个 GAIA 案例，14 个存在 GT 不确定性。p.4 · §3

方案｜切分 → 假设 → 修改 → 重放

  • 切分：LLM 在完整日志中找计划/重新规划边界，再逐 trial 分析。
  • 假设：输出可疑 Agent、步骤索引及自然语言理由。
  • 修改：纠正协调者发给子 Agent 的消息，或重排/替换高层计划。
  • 重放：保留干预点之前的步骤，从原状态继续执行；每个干预产生一条新轨迹。

p.6 · §4.1

干预作用域｜动了什么

  • 指令：澄清目标、改参数、补上下文，间接改变子 Agent 行为。
  • 计划：改变高层路线，绕开被诊断的失败点。
  • 边界：主体实验不改子 Agent 代码，也不生成新工具。

p.6 · §4.1

评估分三层｜不能混用分母

  • 成功率：干预后的 trial 运行最终成功的比例。
  • 进度：较原轨迹多完成了多少里程碑。
  • 假设结论：结合成功次数、进度与执行忠实度分类。

p.7 · §4.2

实验角色｜执行者与评价者分开

  • 执行与调试：GPT-4o 生成轨迹、提出干预并续跑。
  • 评估：GPT-5 判进度与假设验证结果。
  • 框架：Magentic-One / AG2 MathChat；需重采带 checkpoint 的失败轨迹。

p.8 · §5.1

主要结果｜论文 Table 2

  • GAIA-Level-1：27.5% trial 成功率，平均 Progress +15.7%。
  • GSMPlus / AG2：49.0% trial 成功率；这不是 2,400 题总体准确率。

p.5 · Fig.2 · §4

恢复什么｜AG2 的具体接入

  • History：历史消息、说话者与工具输出。
  • Agent config：角色、提示词和工具绑定。
  • LLM config：模型、温度与解码参数。
  • MathChat 无额外持久外部环境；这个条件不能直接推广到浏览器或有副作用的工具。

p.21 · Appendix C

里程碑公式｜进度可正可负

Prog = [A(τ̃) − A(τ)] / K
p.7 · §4.2
  • A 是达成的里程碑数；τ 与 τ̃ 是原轨迹及干预后轨迹。
  • K≤5；从问题、参考答案与人工步骤中抽取关键里程碑，再由 LLM 核验轨迹。
  • 区间 [−1,1]；负值是倒退，0 是没有新增进度。
  • GSMPlus 无人工步骤，论文未计算此项。

p.7 · §4.2

判定协议｜每次干预独立执行 3 次

  • Validated：至少 2/3 次最终成功。
  • Partially Validated：成功不足 2 次，但至少 2 次忠实执行，并达到文中的 20% 新增进度阈值。
  • Refuted：成功不足 2 次；至少 2 次忠实执行，进度却未超过 20%。
  • Inconclusive：其余情况，例如 Agent 根本没有执行新指令。
  • 20% 等号边界：原文措辞重叠，未核对实现，不能自行补一个判定规则。

p.7 · §4.2 · 四类判定

两个实测案例｜为什么会是不同结论

  • Validated：将无目标的 APOD 滚动改为限定日期和关键词检索，最终找到正确建筑事务所。
  • Partially Validated：转向正确金融数据源，但脚本/API 摩擦阻止完成，属于方向改善而非完整成功。

p.22 · Appendix D

工程前提｜不只是把日志贴进提示词

  • 保存 checkpoint → 恢复 manager/agents → 改目标步骤消息 → 从该步续跑。
  • 作者 AG2 接入经验约千行代码、单工程师数天；这是具体案例的工程量。

计量限制｜缺少标注时留空

  • Progress 需要可核验的里程碑；不能拿最终答案相似度自行替代论文指标。
  • 每个干预重复三次，用于减轻一次运行的随机性。

p.7 · §4.2

作者局限｜系统和评估的范围

  • 需要丰富日志与 checkpoint/replay；异步、黑盒框架需要额外 instrumentation。
  • 未覆盖长期生产负载、严格延迟/成本约束、安全关键场景。
  • 里程碑与忠实执行判定部分依赖 LLM judge。

  • 证明某些失败可被消息/计划干预修复；一次成功并不证明唯一根因。
  • 只读这份论文不能视作接入成功或实验复现。

核心思路

把失败归因当作待检验的假设：针对可疑规划或消息做局部修改，恢复状态后重跑，用结果检验诊断是否有用。

以前文章的问题 → 本文如何解决

已有做法与具体不足本文的对应设计
Who&When 等静态归因只输出责任位置，未检验改动是否有效在定位后增加状态恢复、干预和真实续跑。
仅反思最终答案难以改变已经走错的工具交互路径修改中间计划或消息，再让系统重新行动。

依据本文引言、相关工作及方法压缩整理；对照仅针对列出的做法。

创新点｜具体改了什么

  • 把归因与可执行干预组成闭环，区分诊断正确和修复有效。
  • 按 trial 组织长轨迹，并用成功与部分进度共同解释干预结果。
最吸引人的点 （整理者判断）

它让“我觉得这里错了”变成“改掉这里后，系统真的会改变吗？”

创新点为贡献归纳，不作未经全面核验的首次声明；亮点为整理者判断。
